Cara kerja sistem pemantauan kebakaran hutan

Penjelasan alur data dari sensor ESP32 sampai muncul di dasbor, peran run_backend.bat, protokol yang dipakai, dan arti istilah-istilah teknisnya — tanpa perlu latar belakang IT.

Ringkasan 1 menit

  1. ESP32 membaca sensor (suhu, kelembapan, gas/asap, kelembapan tanah), menghitung skor risiko 0–100, lalu mengirim satu paket data bernama JSON ke broker MQTT setiap 3 detik (mode uji realtime; produksi 45 detik).
  2. Broker itu seperti kantor pos: ia tidak mengolah data, hanya meneruskan pesan ke siapa pun yang berlangganan topik tertentu.
  3. Ada dua pelanggan: dasbor di browser (untuk tampilan live) dan pencatat Python di PC Anda (untuk menyimpan ke database).
  4. Pencatat memvalidasi data lalu menulis ke Supabase. Hanya data yang tersimpan di Supabase yang masih ada setelah halaman di-refresh.
  5. Dasbor mengambil riwayat dari Supabase lewat /api/*, dan mengambil angka detik-terkini langsung dari broker.

Alur besar sistem

Baca dari kiri ke kanan. Garis putus-putus = data live (cepat, tidak disimpan). Garis penuh = data yang disimpan.

garis putus-putus: data live, hanya di memori browser jalur penyimpanan permanen baca riwayat dari database

Kalau run_backend.bat tidak dijalankan

Dasbor tetap “hidup”, tetapi hanya setengah sistem yang bekerja.

Dengan pencatat

  • Angka live dari broker tampil.
  • Setiap 3 detik data disimpan ke Supabase (mode uji realtime).
  • Refresh halaman → data terbaru tetap muncul.
  • Grafik 1 jam / 24 jam / 30 hari terisi.
  • Riwayat kejadian (node online/offline, risiko naik) tercatat.
  • Notifikasi Telegram terkirim saat risiko tinggi.
  • Bot Telegram menjawab /status, /suhu, /tren, dan pertanyaan bebas.
  • Data lebih tua dari 90 hari dibersihkan otomatis.

Tanpa pencatat

  • Angka live tetap tampil — tapi hanya sementara.
  • Tidak ada satu baris pun masuk database.
  • Refresh halaman → angka live hilang, kembali ke data lama.
  • Grafik riwayat membeku di titik terakhir yang tersimpan.
  • Rantai status di dasbor menandai Pencatat merah (heartbeat basi).
  • Telegram tidak pernah berbunyi.
  • Tidak ada pembersihan data lama.

Perjalanan satu paket data

Contoh nyata yang terekam saat sistem diperiksa: suhu 29,4 °C · gas 391 · skor risiko 48.

Tahap 1 · alat

Sensor membaca lingkungan

BME280 (I2C: SDA GPIO21, SCL GPIO22) membaca suhu, kelembapan udara, dan tekanan; MQ-2 membaca gas/asap; sensor tanah membaca kelembapan tanah. Firmware menghitung skor risiko 0–100 dari empat komponen lingkungan itu (tekanan tidak masuk rumus).

Tahap 2 · firmware

Data dibungkus jadi JSON

Firmware menyusun teks seperti {"suhu":29.4,"kelembapan":65,"gas":391,"gas_excess":313,"riskScore":48,...} lalu mengirim (publish) ke topik …/esp32-01/sensor.

Tahap 3 · jaringan

Broker menerima & meneruskan

Broker HiveMQ menerima pesan dan meneruskannya ke semua pelanggan topik tersebut. Broker tidak menyimpan riwayat jangka panjang dan tidak mengolah angka.

Tahap 4 · dasbor

Browser menampilkan angka live

Dasbor berlangganan topik yang sama lewat WebSocket. Dalam hitungan milidetik angka di layar berubah. Data ini masih di memori — belum tersimpan di mana pun.

Tahap 5 · pencatat

Pencatat memvalidasi

Program Python menerima pesan yang sama, memeriksa kewajaran nilai (mis. suhu mustahil dibuang), lalu menyiapkan baris database.

Tahap 6 · database

Ditulis ke Supabase

Baris masuk ke tabel readings: waktu, suhu, gas, skor, status. Pencatat juga memperbarui node_status dan denyut backend_heartbeat tiap 30 detik.

Tahap 7 · setelah refresh

Dasbor membaca riwayat lewat API

Browser memanggil /api/latest dan /api/series. Server Vercel (yang memegang kunci database) mengambil data dari Supabase dan mengirimkannya tanpa rahasia. Karena berasal dari database, angkanya tetap ada.

Protokol yang dipakai

“Protokol” = kesepakatan cara dua program berbicara. Project ini memakai lima percakapan berbeda.

Alat → Broker → Pencatat

MQTT TCP 1883 / TLS 8883

Protokol pesan ringan untuk perangkat IoT. Pengirim publish ke sebuah topik; penerima subscribe topik itu. Tidak ada yang “meminta”; pesan mengalir begitu saja.

Analogi: grup chat. ESP32 mengirim ke grup “sensor”, semua anggota grup menerima.

Broker → Browser

WebSocket / WSS port 8884

Browser tidak bisa bicara MQTT langsung, jadi MQTT dibungkus ke WebSocket. WSS = versi aman (terenkripsi) dari WebSocket.

Analogi: telepon yang tidak ditutup — koneksi tetap terbuka agar pesan baru langsung masuk.

Browser → Vercel → Supabase

HTTPS / REST JSON

Permintaan sekali-jalan: “beri saya data terakhir”. Setiap alamat seperti /api/latest disebut endpoint. Jawabannya JSON.

Analogi: memesan makanan lewat aplikasi — minta, lalu diantar sekali; tidak ada saluran yang tetap terbuka.

Pencatat → Supabase

PostgREST HTTP + SQL

Supabase mengekspos tabel PostgreSQL sebagai alamat HTTP. Menulis satu baris = POST /rest/v1/readings. Tidak perlu menulis SQL manual.

Analogi: database yang bisa menerima pesanan lewat formulir web.

Format isi pesan

JSON

Format teks berpasangan nama–nilai: {"suhu": 29.4}. Dipakai di MQTT, API, dan database agar mudah dibaca manusia maupun program.

Analogi: formulir dengan kolom bernama.

Keamanan

TLS + kunci rahasia

TLS membuat isi pesan tidak bisa dibaca di tengah jalan. Kunci service_role hanya ada di server Vercel dan di PC pencatat — tidak pernah dikirim ke browser.

Analogi: amplop tersegel + kunci gudang yang hanya dipegang petugas.

Mengapa pencatat tidak bisa di Vercel? Vercel menjalankan serverless function: kode hanya hidup beberapa detik saat dipanggil, lalu dimatikan. MQTT butuh koneksi yang terbuka terus-menerus. Karena itu pencatat harus berupa program yang berjalan lama — di PC, laptop, atau server.

Istilah di project ini

Dikelompokkan supaya mudah dicari. Istilah Inggris ditulis miring.

Perangkat & jaringan
Node
Satu titik pemantauan. Di project ini satu node = satu ESP32 dengan ID esp32-01.
ESP32
Microcontroller mungil ber-WiFi. Otak di sisi alat: membaca sensor, menghitung skor, mengirim data.
Firmware (sketch)
Program yang ditanam di ESP32. Di project ini: antikobongan-2.ino. Menanamnya disebut flash.
MQ-2 / BME280
Sensor gas/asap dan sensor suhu-kelembapan-tekanan. MQ-2 belum dikalibrasi ke satuan ppm, jadi angkanya “indeks”, bukan konsentrasi resmi. BME280 memakai I2C (VIN/VCC → 3V3, GND, SCL → D22, SDA → D21).
MQTT
Protokol pesan ringan untuk IoT. Modelnya publish–subscribe lewat broker.
Broker
Server perantara pesan MQTT. Project ini memakai broker publik broker.hivemq.com.
Topik (topic)
“Nama saluran” pesan, mis. antikobongan/prototipe-gx7q4m/esp32-01/sensor. Penerima hanya menerima topik yang di-subscribe.
Publish / Subscribe
Publish = mengirim pesan ke topik. Subscribe = berlangganan topik untuk menerima pesan.
Payload
Isi pesan itu sendiri — di project ini berupa JSON berisi suhu, gas, skor, dan waktu.
QoS
Tingkat jaminan pengiriman. Project ini memakai QoS 0: dikirim sekali, tanpa konfirmasi — cepat, tapi bisa hilang jika jaringan putus.
Retained message
Pesan terakhir yang disimpan broker untuk topik tertentu, sehingga pendatang baru langsung tahu status terakhir. Dipakai untuk topik status.
LWT (Last Will and Testament)
“Surat wasiat”: pesan offline yang otomatis diumumkan broker bila ESP32 terputus mendadak.
WebSocket
Koneksi dua arah yang tetap terbuka antara browser dan server. Dipakai dasbor untuk menerima MQTT.
WSS
WebSocket yang dienkripsi TLS (aman). Alamatnya diawali wss://.

JSON
Format teks untuk data berstruktur, mis. {"suhu":29.4,"gas":391}.
Supabase
Layanan database berbasis PostgreSQL + API otomatis. Menyimpan seluruh riwayat pembacaan.
PostgreSQL / Postgres
Jenis database relasional: data disimpan dalam tabel berbaris dan berkolom.
Tabel / baris / kolom
Tabel = lembar data. Baris = satu catatan (satu pembacaan). Kolom = jenis nilai (suhu, gas, waktu).

Tabel utama: satu baris per pembacaan sensor.

Stale / basi
Data yang umurnya melewati batas dianggap bukan kondisi sekarang. Pada mode uji realtime (interval 3 detik), batasnya 15 detik; pada produksi (interval 45 detik) batasnya 180 detik. Status node dari broker (online/offline) dibedakan dari status data sensor.
Retensi (retention)
Kebijakan menghapus data lama otomatis. Di project ini 90 hari.
SQL
Bahasa untuk mengelola database: membuat tabel, mengambil, menghapus.
Migrasi (migration)
File perubahan struktur database, mis. sql/002_series.sql yang menambah kolom dan fungsi agregasi.
RPC / fungsi database
Perhitungan yang dijalankan di dalam database, mis. reading_series yang merangkum data per rentang waktu agar cepat.
PostgREST
Lapisan Supabase yang mengubah tabel database menjadi alamat HTTP.
Agregasi / bucket

Pertanyaan yang sering muncul

Kalau PC dimatikan, apa yang terjadi?

ESP32 tetap mengirim, dasbor tetap menampilkan live selama ada yang membuka halaman. Tapi tidak ada data baru yang tersimpan. Saat PC menyala lagi dan pencatat dijalankan, penyimpanan lanjut — data selama PC mati tidak bisa dipulihkan (QoS 0, broker tidak menyimpan riwayat).

Kenapa data lama terlihat “datar” dan aneh?

Itu baris hasil impor CSV (data sintetis): suhu nyaris konstan, gas_excess kosong. Data asli mudah dikenali: nilainya bervariasi dan gas_excess terisi.

Apakah dasbor bisa menulis ke database?

Tidak. Browser hanya membaca lewat API. Penulisan hanya dilakukan pencatat (dan panel admin untuk daftar node, memakai PIN). Ini disengaja agar kunci rahasia tidak pernah ada di browser.

Kalau internet putus sebentar?

ESP32 dan pencatat menyambung ulang otomatis. Pesan yang gagal terkirim saat putus tidak diulang. Pencatat punya antrean kecil dan mencoba ulang 3 kali bila database sedang bermasalah.

Kenapa harus ada .env?

Isinya alamat dan kunci rahasia. Dipisahkan dari kode agar tidak ikut terunggah ke GitHub. File backend/.env sudah diabaikan Git.

Bagaimana cara memastikan pencatat bekerja?

Lihat backend\logs\backend.log. Baris Data valid: suhu=… berarti data diterima dan disimpan. Di dasbor, rantai status bagian Pencatat hijau bila heartbeat masih segar.
